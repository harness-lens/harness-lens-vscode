# npm 0.0.5 release incident

## Summary

VS Code release `v0.0.5` completed its builds, tests, SBOMs, attestations, and
GitHub asset upload, but npm publication failed. The release tag and assets
remained valid and immutable. Registry-only recovery published the existing
checksum-verified tarball as `@harness-lens/vscode@0.0.5`; no artifact was
rebuilt, replaced, or reattached.

Marketplace publication was independently disabled and was not part of this
incident.

## Impact

- GitHub release assets, including the VSIX and Windows language server, were
  available and valid.
- npm continued to expose only `0.0.1` until recovery completed.
- No source, secret, credential, or rebuilt artifact entered a report or release.

## Causes

Two independent faults blocked publication:

1. `npm publish artifacts/harness-lens-vscode-*.tgz` used a bare relative path.
   npm parsed the expanded `artifacts/...` value as GitHub shorthand and tried
   an SSH Git URL. Prefixing the local path with `./` made its type unambiguous.
2. npm trusted publishing had no registered publisher for the package.
   `setup-node`'s `registry-url` input also generated an empty `_authToken`
   placeholder, initially hiding the OIDC exchange behind a misleading `E404`.

## Timeline and evidence

- [Release run 34819302107](https://github.com/harness-lens/harness-lens-vscode/actions/runs/34819302107)
  built and uploaded valid `v0.0.5` assets, then failed npm publication because
  the tarball path was parsed as GitHub shorthand.
- [PR 41](https://github.com/harness-lens/harness-lens-vscode/pull/41)
  added explicit local-path publication and checksum-verified registry-only
  recovery.
- [Recovery run 34820849382](https://github.com/harness-lens/harness-lens-vscode/actions/runs/34820849382)
  verified every release checksum, then exposed the empty-token authentication
  failure.
- [PR 42](https://github.com/harness-lens/harness-lens-vscode/pull/42)
  removed `registry-url` from npm publishing jobs so npm could use GitHub OIDC.
- [Recovery run 34821342175](https://github.com/harness-lens/harness-lens-vscode/actions/runs/34821342175)
  reached npm without classic credentials and failed `ENEEDAUTH`.
- [Diagnostic dry-run 34821631457](https://github.com/harness-lens/harness-lens-vscode/actions/runs/34821631457)
  proved GitHub ID-token issuance succeeded, while npm's exchange endpoint
  returned `package not found`. An authenticated audit confirmed zero trusted
  publishers for the package.
- A maintainer registered `release.yml` for
  `harness-lens/harness-lens-vscode`, environment `npm`, with direct publish
  permission.
- [Recovery run 34822418688](https://github.com/harness-lens/harness-lens-vscode/actions/runs/34822418688)
  verified all immutable assets and published `@harness-lens/vscode@0.0.5` with
  registry-generated SLSA provenance.

## Validation

Final public registry evidence showed:

- version `0.0.5` present and `dist-tags.latest` set to `0.0.5`;
- tarball SHA-1 `09b1ddfd161a6037b0735da03751993ee24c38a6`;
- SHA-512 integrity metadata, registry signatures, and SLSA provenance;
- public version and tarball endpoints returning HTTP `200`.

Initial `npm view` requests briefly returned cached `0.0.1` metadata after the
successful publish. Cache-busted public endpoints already exposed `0.0.5`.
No additional publish was attempted.

## Preventive controls

- Require exactly one `./artifacts/harness-lens-vscode-*.tgz` before publish.
- Recover only from existing release assets after complete `SHA256SUMS`
  verification.
- Keep npm recovery independent from rebuild, upload, and other registries.
- Keep npm trusted-publisher identity explicit and auditable.
- Do not generate an empty classic-token placeholder in OIDC jobs.
- Treat recovery as single-use and verify public registry state before retrying.
- Use verbose dry-run diagnostics; never diagnose by repeatedly publishing.
